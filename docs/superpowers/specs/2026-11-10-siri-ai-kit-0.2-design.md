# SiriAIKit 0.2.0: Siri-specific helpers only

Builds on [2026-11-10-siri-ai-kit-design.md](2026-11-10-siri-ai-kit-design.md) (0.1.0, published today as `airowe/siri-ai-kit` 0.1.0).

## Why

0.1.0 shipped its own auth: a Keychain token store, a refresh coordinator and an HTTP client. In an app that already has users, that becomes a second auth system:

- **Existing tokens:** they're saved in the app's own format, so the library's store can't read them.
- **Racing refreshes:** the app's networking and the tool both refresh, and if the API issues a new refresh token on every refresh, one side gets rejected and the user is signed out.
- **Duplicate HTTP client:** the app already has one, so the library's is extra code to maintain.

Auth belongs to the app. The library should only cover what Siri adds on top.

**Goal:** let a developer wrap the API code they already have in a Siri tool, and test it with Siri Evaluations, without adopting anything else from the library.

**Success:**
- A tool body built from the app's own API call is one wrapper call.
- The example app passes the same device evaluations as 0.1.0: cart 5 of 5, expired token 5 of 5, and a negative control that fails as it should.
- No SiriAIKit type touches tokens, the Keychain or HTTP.

## What changes

| 0.1.0 | 0.2.0 |
|---|---|
| `Tokens`, `TokenStore`, `KeychainTokenStore`, `KeychainAccessibility` | Removed |
| `TokenAuthenticator`, `SingleResume` | Removed. The internal `SingleResume` helper stays and `SiriTool` reuses it |
| `ToolHTTPClient`, `HTTPMethod` | Removed |
| `ToolError` (`signedOut`, `timedOut`, `unreachable`, `rejected`, `invalidResponse`, `keychain`) | Replaced by `ToolFailure` (`signedOut`, `timedOut`, `unreachable`, `failed`) |
| `ToolReplies`, `error.reply(appName:)` | Kept, now on `ToolFailure` |

| — | New: `SiriTool` |
| — | New: `KeychainLockCheck` (debug only) |

Version 0.2.0. It breaks the 0.1.0 API, which semver allows before 1.0. 0.1.0 has been public for less than a day.

## `SiriTool`

```swift
public struct SiriTool: Sendable {
    public init(
        appName: String,
        timeout: Duration = .seconds(10),
        replies: ToolReplies = .default,
        outcomes: ToolOutcomeLog = .standard,
        classify: @escaping @Sendable (any Error) -> ToolFailure? = { _ in nil }
    )

    /// The operation's value, or a `ToolFailure` if it threw or ran past `timeout`.
    public func run<T: Sendable>(_ operation: @escaping @Sendable () async throws -> T) async throws(ToolFailure) -> T

    /// The operation's answer, or the sentence Siri should say instead.
    public func answer(_ operation: @escaping @Sendable () async throws -> String) async -> String
}
```

Usage:

```swift
let tool = SiriTool(appName: "My App") { error in
    (error as? MyAPIError) == .unauthorized ? .signedOut : nil
}

func perform() async throws -> some IntentResult & ReturnsValue<String> & ProvidesDialog {
    let answer = await tool.answer { describe(try await MyAPI.shared.cart()) }
    return .result(value: answer, dialog: "\(answer)")
}
```

How each failure is classified, in order:

1. If `classify` returns a value, that value is used.
2. A thrown `ToolFailure` is used as is.
3. `CancellationError`, or `URLError` `.timedOut` or `.cancelled`, gives `.timedOut`.
4. Any other `URLError` gives `.unreachable`.
5. Anything else gives `.failed`.

**Deadline.**
- At `timeout`, or when the caller is cancelled (Siri gives up), `run` throws `.timedOut` right away.
- The operation is not cancelled. It keeps running so the app's own auth can finish: a refresh that already used the refresh token must still save the new tokens.
- Ruling: we accept that background work can run on past the deadline, in exchange for never leaving the app's tokens half-rotated. The cost if wrong: work that runs on after Siri has given up.
- Implementation: an unstructured task, with the caller waiting through `SingleResume` and its deadline race, the same pattern 0.1.0 used for refresh.

**Outcomes.**
- Each run starts by clearing any pending notes.
- During the run, the app's code can call `ToolOutcomeLog.standard.note("refreshed after 401")`.
- When the run ends, the wrapper records the result with the notes, joined by "; ": "succeeded (refreshed after 401)", "signed out", "timed out", "unreachable" or "failed".
- The " at <time>" suffix stays.

`ToolFailure.reply(appName:overrides:)` maps each case to a sentence:

| Case | Sentence |
|---|---|
| `.signedOut` | the signed-out sentence |
| `.timedOut`, `.unreachable` | the unreachable sentence |
| `.failed` | the failed sentence |

The default wording is the same as 0.1.0.

## `KeychainLockCheck` (debug only)

Siri can run a tool while the phone is locked. Tokens saved with `WhenUnlocked` protection, the default in some secure-storage libraries, can't be read then. The spike measured this and 0.1.0 handled it inside its own store. 0.2.0 helps the app check its own store instead:

```swift
#if DEBUG
/// Logs a warning if the Keychain item can't be read while the phone is locked.
public enum KeychainLockCheck {
    public static func warnIfLockedOut(service: String, account: String? = nil)
}
#endif
```

- It reads the item's `kSecAttrAccessible` value.
- It warns once with `os.Logger` unless the value is `AfterFirstUnlock`, `AfterFirstUnlockThisDeviceOnly`, or the deprecated `Always` or `AlwaysThisDeviceOnly`. Those are the only values readable while the phone is locked.
- It's silent when the item is missing, so a signed-out app doesn't warn.
- The decision lives in a pure function, `isReadableWhenLocked(_ accessible: CFString) -> Bool`, which is unit tested. The Mac's Keychain ignores accessibility, so that part is checked only on a device, through the example app.

## Example app

`DemoAPI` keeps its own auth, written as the app's code rather than the library's:
- A small Keychain helper that saves with `AfterFirstUnlockThisDeviceOnly`.
- A refresh on 401 that calls `ToolOutcomeLog.standard.note("refreshed after 401")`.
- Plain `URLSession`.

It calls `KeychainLockCheck.warnIfLockedOut` at launch in debug builds. `GetCartIntent` uses `tool.answer { … }`. The evaluations are unchanged.

This code lives in the example, not the library. The README points to it as the pattern for refreshing inside a Siri request.

## Testing

`swift test` on the Mac:

- **`SiriTool`:**
  - **Success:** returns the value and records "succeeded".
  - **Classification:** each step of the failure order, including `classify` winning over the default rules.
  - **Timeout:** `.timedOut` returns within the timeout plus 0.5 s, and the operation isn't cancelled. Checked by the operation finishing and setting a flag after the deadline.
  - **Caller cancelled:** gives `.timedOut`.
  - **Notes:** appear in the recorded outcome, and they're cleared between runs.
  - **`answer`:** returns the reply sentence for each failure.
- **`KeychainLockCheck`:** a parameterized test of `isReadableWhenLocked` covering every accessibility constant.
- **Removed types:** their tests go too.

On a device, before tagging, the example evaluations:
- Cart, 5 runs.
- Expired token, 5 runs.
- Negative control with refresh off, 1 run, which must fail with the signed-out reply.

The results go in the README table.

## Out of scope

- **Any shared refresh or cross-process lock:** that's the app's auth.
- **The Expo / React Native layer** (`expo-siri-ai`): a later project, which this API makes simpler since the module only wraps `SiriTool`.
- **Filing 0.1.0's deferred minors:** most of them were in the removed auth code. I'll recheck the rest against 0.2.0 when planning.
